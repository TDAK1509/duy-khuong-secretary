# Trợ lý

A Vietnamese Zalo secretary for transportation companies. Drivers upload receipts, weigh tickets, invoices, photos and texts, and the app stores them in an organized way. Admins upload too, state standing facts about trips, vehicles and drivers, and ask for reports and analyses of the saved data. One TypeScript package (Node 24, npm).

## Run it locally

```sh
docker compose up -d --wait
npm ci
npm run build
DATABASE_URL=postgres://app_runtime:app_runtime@localhost:5432/secretary npm start
curl -i http://localhost:3000/health
```

`docker compose up` starts Postgres 17 with the database `secretary`, owned by the role `app_owner`. That role is not a superuser. It also creates the role `app_runtime`, which the service uses. Run the migrations as `app_owner` (see Migrations) before you start the service. If port 5432 is taken, set `POSTGRES_PORT` before `docker compose up` and use that port in `DATABASE_URL`.

| Env var | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | derived when unset | Postgres connection string of the runtime role `app_runtime` (see Row-level security). When unset, the service builds it from `MIGRATION_DATABASE_URL` and `APP_RUNTIME_PASSWORD`. The start fails when neither way works |
| `PORT` | `3000` | HTTP port |
| `GIT_COMMIT` | `RENDER_GIT_COMMIT`, else none | The deployed commit, shown by `/health` |
| `MIGRATION_DATABASE_URL` | none | Direct connection as the schema-owner role. Read by `node dist/bootstrap/migrate.js`, and by the service when `DATABASE_URL` is unset (only the host, port, database and query are used) |
| `APP_RUNTIME_PASSWORD` | none | Password of `app_runtime`. `migrate.js` sets it after the migrations, and the service signs in with it when `DATABASE_URL` is unset. On Render, Render generates it |

`GET /health` answers `200 {"ok":true,"commit":"<sha>"}` when the database answers, and `503 {"ok":false,"commit":"<sha>"}` when it does not. `commit` is `GIT_COMMIT`, else `RENDER_GIT_COMMIT`, else `null`.

## Create a workspace

The operator creates a workspace and the invite code of its first admin with one command (needs `DATABASE_URL`, or `MIGRATION_DATABASE_URL` with `APP_RUNTIME_PASSWORD`, and the migrations applied):

```sh
npm run build
DATABASE_URL=postgres://app_owner:app_owner@localhost:5432/secretary node dist/bootstrap/create-workspace.js "Xe tải Duy Khương" "Duy"
```

It prints `Workspace "<name>" created: <id>` and `First admin invite for <admin>: MOI-XXXXXX (valid until HH:mm dd/MM/yyyy)`. The code works once and for 7 days. Only its SHA-256 hash is stored, so the printed code is the only copy. Every run creates a new workspace. A name that is empty after trimming prints `Invalid workspace name.` or `Invalid admin name.` (exit 1) and creates nothing. On Render, run the same command in the service shell as `node dist/bootstrap/create-workspace.js "<workspace>" "<admin>"`.

## Connect the Zalo OA

The service talks to one shared Zalo Official Account. The operator connects it once:

```sh
npm run build
node dist/bootstrap/connect-zalo.js
```

It prints a link. Open it in a browser logged in to Zalo as an OA admin and approve. The browser shows `Zalo OA <oa id> connected.` and `channel_connections` holds one row for the OA with its keys encrypted (AES-256-GCM, `CHANNEL_TOKEN_ENCRYPTION_KEY`). On Render, run the same command in the service shell. Set the Zalo app's callback URL to `<PUBLIC_BASE_URL>/oauth/zalo/callback`.

Every 60 seconds the service renews each connection whose access key expires within 60 minutes. A rejected or unreachable renewal keeps the keys, alerts the operator and tries again on the next tick. A renewal that gets no answer may have spent the single-use renewal key: the connection becomes `reauthorization_required`, automatic renewal stops, and the operator is alerted. Run `connect-zalo` again before the access key expires (25 hours). The same alert text is sent at most once per hour per process.

The `zalo` feature group is on only when `MESSAGING_PROVIDER`, `ZALO_APP_ID`, `ZALO_APP_SECRET`, `CHANNEL_TOKEN_ENCRYPTION_KEY` and `PUBLIC_BASE_URL` are all set. While it is off the service logs `[config] zalo is off; missing: <NAMES>.`, the callback answers `503 Zalo is not configured.`, renewal is skipped, and `connect-zalo` prints `zalo is not configured: missing <NAMES>.` (exit 1).

| Env var | Default | Meaning |
|---|---|---|
| `MESSAGING_PROVIDER` | none | `zalo-oa` |
| `ZALO_APP_ID`, `ZALO_APP_SECRET` | none | The Zalo app's id and secret key |
| `ZALO_OAUTH_BASE_URL` | `https://oauth.zaloapp.com` | Zalo OAuth host |
| `ZALO_API_BASE_URL` | `https://openapi.zalo.me` | Zalo API host (sending messages) |
| `ZALO_BUSINESS_API_BASE_URL` | `https://openapi.zalo.me` | Host of the template message call `POST /v3.0/oa/message/template` (ZBS by user id; checked against the Zalo docs; the plan named `https://business.openapi.zalo.me`) |
| `ZALO_TIMEOUT_MS` | `15000` | How long a Zalo API call may take before it counts as unanswered |
| `OUTBOUND_MAX_PER_MINUTE` | `90` | How many Zalo calls go out per minute, at least `2` (the Tăng trưởng package allows 100). An image counts as two calls |
| `CHANNEL_TOKEN_ENCRYPTION_KEY` | none | 64 hex characters, or base64 of exactly 32 bytes (the form Render generates). Any other value stops the start |
| `PUBLIC_BASE_URL` | `RENDER_EXTERNAL_URL`, else none | Public URL of this service, for example `https://duy-khuong-secretary.onrender.com`. Set it only for a custom domain |
| `ZALO_VERIFIER_FILE_NAME`, `ZALO_VERIFIER_FILE_CONTENT` | none | Both optional. When both are set, `GET /<file name>` returns the content as `text/html` (Zalo domain verification) |
| `ZALO_MEDIA_HOSTS` | `zdn.vn,zadn.vn,dlfl.vn` | Comma-separated hosts that photo and file downloads may use. `dlfl.vn` was seen as the file host in a verified Zalo webhook; its ownership is not confirmed. A host matches when it equals an entry or ends with `.` plus an entry |
| `ZALO_OA_SECRET` | none | The OA secret key shown in the Zalo app's webhook settings; turns the webhook on |
| `ALERT_PROVIDER` | `log` | `log` writes alerts to the error log; `webhook` posts `{"text":"..."}` to `ALERT_WEBHOOK_URL` |
| `ALERT_WEBHOOK_URL` | none | Required when `ALERT_PROVIDER=webhook`; the start fails without it |

## Receive Zalo messages

`POST /webhooks/zalo` takes every event Zalo sends to the OA. In the Zalo app's webhook settings, set the URL to `<PUBLIC_BASE_URL>/webhooks/zalo` and turn on `user_send_text`, `user_send_image` and `user_send_file`. Set `ZALO_OA_SECRET` to the OA secret key shown there.

The route checks the `X-ZEvent-Signature` header (`mac=` and the hex SHA-256 of app id, exact raw body, `timestamp` and OA secret key) and that the body's `app_id` is `ZALO_APP_ID`. Answers:

| Status | When | Stored |
|---|---|---|
| `200 {"ok":true}` | A text or image message from a connected OA, a resent message, or any other event | One `queued` row in `inbound_events` for a new text or image message |
| `401 {"ok":false}` | The signature or the `app_id` is wrong | Nothing |
| `200 {"ok":true}` | An event for an OA that is not in `channel_connections`, such as Zalo's webhook check, which uses a sample OA id | Nothing; the service logs `[webhook] event for an OA that is not connected: <oa id>` |
| `500 {"ok":false}` | The connection check or the insert failed | Nothing; the operator gets `[alert] Zalo webhook could not store an event: <error name>.` |
| `503 {"ok":false}` | The `zalo-webhook` group is off: the `zalo` group plus `ZALO_OA_SECRET` | Nothing |

The service logs `[config] zalo-webhook is off; missing: <NAMES>.` while the group is off. The body limit is 1 MB. The background worker then marks each stored event `done`, in order per sender, and records the sender in `channel_identities`.

When the worker picks up a message from a sender whose current membership is `admin` (text, photo or album, file; not an invite code, workspace switch, bare-number choice or internal command), on the event's first pickup only (first attempt, never postponed, handed back or retried: `available_at` still equals `received_at`) and before any other work, it reacts 👍 to that Zalo message: one direct `POST /v3.0/oa/message/cs` (the reply path; the documented `/v2.0/oa/message` answers error -212 for this app) with `sender_action.react_icon` `/-strong` and `react_message_id` the message's `msg_id`, outside the outbound queue and its per-minute limit. An album is one message and gets one 👍. It is best effort: no retry and no alert, and the answer is handled as usual either way. It logs `[reaction] sent event=<inbound event id>` or `[reaction] failed event=<inbound event id> reason=<reason>`. When Zalo refuses it with an error code, the line before it is `[zalo] send rejected: error <code>`. Members get no reaction.

## Send Zalo replies

Replies wait in the `outbound_messages` table (one row per message, at most 2,000 characters each) and a background worker sends them to Zalo one at a time, in order per person. The worker does nothing while the `zalo` group is off. Everyone who writes to the OA gets the welcome text until joining with an invite code exists.

| Status | Meaning |
|---|---|
| `queued` | Waits for its turn or for a retry (`available_at`) |
| `sending` | Claimed by the worker (`locked_until` is 2 minutes ahead) |
| `sent` | Zalo accepted it |
| `failed` | Zalo refused it, or the retries ran out |
| `unknown` | The request may have reached Zalo but no answer came back. It is never sent again |

The worker makes at most `OUTBOUND_MAX_PER_MINUTE` Zalo calls in any 60 seconds. An image counts as two calls (upload and send). A message is claimed only when the calls of the last 60 seconds (sent plus still sending) plus its own stay within the limit. Zalo's rate-limit error waits 60 seconds and retries up to 10 attempts. A request that never left the server (connection refused, DNS failure) waits 30 s, 60 s, 120 s, ... and fails after 5 attempts. A missing OA connection waits 60 s and fails after 5 attempts. A `sending` row whose lock passed becomes `unknown`.

The operator gets `[alert] Zalo send got no answer for outbound message <id>. It will not be resent. Check the chat in OA Manager.` for each `unknown` message, `[alert] Outbound message <id> failed after <n> attempts.` when retries run out, and `[alert] No Zalo connection for OA <oa id>. Run connect-zalo.` while the OA has no stored keys. A row with `admin_membership_id` is sent only while that membership exists; otherwise it becomes `failed` (`membership_changed`).

## Store photos and texts

Everything a person in a workspace sends is stored in the `messages` table, in their chat of the workspace they chose. A photo is downloaded from Zalo at once and kept in the private bucket (see "Object keys" below). Every reply is also stored as a bot message. A photo over 5 MB, a file that is not JPEG or PNG (the first bytes are checked; the server never decodes the image), or a download that fails gets its own reply and stores no message.

The download uses `https` only, from a host in `ZALO_MEDIA_HOSTS`. It follows at most 3 redirects, checks each target the same way, and refuses a host whose addresses are loopback, private, link-local, unique-local or unspecified. A refused URL is logged without its query string.

An admin's `.xlsx` or `.csv` file goes through the same download rules. Its bytes are stored in file storage before the `message_files` row is committed, so the parse worker never claims a file whose bytes are not there yet; a retried event reuses the key its stored row already points to. If the bytes are still missing when a file step runs, the step logs `[files] bytes missing file=<id>` and fails with `FileBytesMissingError`, so the usual backoff applies instead of an immediate "unreadable" reply; only after 5 attempts is the give-up reply sent. A failed download is logged as `[intake] file download failed: <reason>` (`host_refused` for a host outside the list, `network` for a connection error or a host whose addresses are not public, `http` for a non-2xx answer or too many redirects; never the URL) and the admin gets "Không tải được file này. Vui lòng gửi lại. Nếu vẫn không được, báo cho người quản trị hệ thống." A file whose bytes are not a real `.xlsx` or `.csv` is logged as `[intake] file is not a sheet: <event id>` and the admin gets "File này không phải file Excel (.xlsx) hoặc CSV đọc được. Kiểm tra lại file rồi gửi lại." A file over 5 MB gets "File quá lớn, tối đa 5 MB." No file event ends without a reply. Both parsers keep each non-empty row with its real row number. An `.xlsx` cell is read from its value and number format, not its display text: a date becomes `YYYY-MM-DD`, a time of day becomes `hh:mm` (seconds cut, as Excel shows it), an elapsed duration (`[h]:mm`) becomes its total `hh:mm`, any other number a plain decimal, text is trimmed. The header is found among the first 10 rows: each row scores its distinct non-empty cells (a merged title that repeats one value scores nothing) plus one for each of the next three rows filled in at least half the same columns; the best row with at least 2 distinct cells wins, else row 1. Rows above it are context lines for the reader (untrusted, like the caption), and the headers reply adds "(dòng tiêu đề: <n>)" when the header is not row 1. The reader answers `column_mapping` as a list of `{column_index, field}` (strict-mode JSON schema) and `date_format`; our code rejects an index outside the header, a column listed twice, not exactly one date column, or a single-valued field used twice, and cuts the document kind to 60 characters. A failed reader API call logs `[reader] api failed status=<status> message=<…>`, and a rejected answer `[sheet-reader] answer rejected reason=<reason>`. Data rows equal to the header, whose first non-empty cell is only "Tổng", "Cộng" or "Tổng cộng" (so "Tổng công ty …" stays a data row), without a readable date, or (when a plate column is mapped) without a plate after `normalizeCode` are skipped and listed by their real row numbers in the result. The title column is optional: without one, the title is "<kind> <plate> <date>". A sheet with more than 5,000 data rows is refused with a request to split it. Each `detail` cell becomes a document line labelled with its header and with that header as its meaning: an `hh:mm` value becomes minutes (unit `phút`), or hours when the header's unit is giờ, except under a time-of-day header such as "Giờ đi" or "Giờ đến", which stays text; a plain decimal becomes a number when the header names a unit, a known word first (km/h, km, kg, tấn, lít → `l`, đ, VND, VNĐ or đồng → `vnd`, phút, giờ) and else a one-word tag in parentheses (for example "(Lần)" → `lần`; "(GPS)" and "(TB)" are not units, and "(1000đ)" is not a unit); money written with dot thousands ("150.000") is read as thousands; any other value, or a number whose header names no unit, stays a text line, because a line's number and unit are stored together or not at all. Totals over these meanings then work like totals from photos. A sheet row's identity is its header signature, plate, date and, when a document-number column is mapped, its number. The header signature is a hash of the match keys of every non-empty header in the header row, in order (blank header cells are left out, since a stray cell elsewhere in a sheet can add blank columns), stored in `documents.sheet_signature`, so the same export format matches itself whatever kind name or column mapping the reader gives it. A second row with the same identity in one upload is skipped as a duplicate. When a saved document has the same identity (a saved document without a document number also matches a row that has one) and every one of its sources is a sheet upload, its lines, title, summary and details are replaced (its kind stays) and the new upload is added as a source, then the document is linked again to the facts it matches; a document with any other source (a photo, a text) is never changed, and the row becomes a new document. All of this happens in the process step's one fenced transaction under the workspace lock, as a few set-based statements for the whole upload, and the result reply reads "Chứng từ \"<kind>\": N dòng mới, M dòng cập nhật, K dòng bỏ qua (dòng …; trùng: dòng …)". After "Đã nhận file", two queue workers finish the sheet, each with concurrency 1 and a 1-second poll: `files-parse` (on when the `zalo` and `photos` groups are on) replies with the headers, and `files-process` (also needs `readers`) has the sheet reader save the rows as documents and replies with the result; otherwise the service logs `[config] files-parse is off; missing: <groups>.` or the same for `files-process`. Each worker claims the oldest sheet in its step (`parsed_at` empty, or parsed but not `processed_at`) whose `locked_until` is empty or past, with `FOR UPDATE SKIP LOCKED`, then sets a fresh `claim_token`, a 5-minute lease and `attempts + 1`. Every later write is scoped to the workspace and matches the sheet's id, token and step, so two instances never both finish a sheet; a write that matches nothing logs `[files] claim lost`. A sheet that cannot be read or has no data rows gets its one reply and is finished at the parse step; one that cannot be parsed again at the process step gets the same reply and is finished, without a reader call. The process step computes everything first (rechecking credits right before the reader call and renewing its lease around it), then writes the documents, its reply and `processed_at` in one transaction under the workspace lock; out of credit, a mapping problem or a reader failure returned as a value gets one final reply, as before. Reader calls are at least once (a crash after a call means a second, metered call); documents and replies are exactly once. A thrown error (database, storage, a bug) releases the sheet for `30 s × 2^(attempts − 1)`, at most 8 minutes, with `last_error` (at most 200 characters); after 5 attempts the next claim only gives up, sending the parse failure or "Trợ lý không đọc được file…" reply and logging `[files] gave up file=<id> step=<step> error=<name>`. When the admin's membership is gone, at either step, the sheet is finished without a reply or saved rows, logged as `[files] admin gone file=<id>`. Every sheet reply quotes the admin's file message, and starts with "Kết quả cho file gửi lúc HH:mm dd/MM:" when the file came more than 30 minutes earlier. On `SIGTERM` both workers stop claiming, held sheets' leases are extended to the deadline plus the lock margin, and at the deadline any sheet still held is handed back (token and lease cleared, `attempts` given back, `last_error` kept), logged as `[shutdown] handed back file=<id>`. Zalo sends a file's caption as its own text event about a second before the file event. So a text event from a current admin waits until 5 seconds after its `sent_at` (postponed without spending an attempt; members' texts are not delayed). It is then linked to the earliest file event from the same sender that is still queued behind it, whose `sent_at` is within those 5 seconds, that is a single file (not "too many files") and that has no caption yet: in the transaction that finishes the text, the text is stored as a message, `inbound_events.caption_for_event_id` points at the file event (a unique index keeps one caption per file), the log says `[intake] text <id> used as caption of file <id>`, and the text gets no reply of its own. A retry cannot link twice: the link and the text's `done` status commit together, and a unique index allows one caption per file. In later chat turns the caption shows as "[ghi chú kèm file, đã dùng để đọc file] …". The wait is capped at 5 seconds from the server's clock, so a skewed `sent_at` cannot delay a text longer. The file intake copies the caption (at most 1,000 characters) to `message_files.caption`, and the sheet reader gets it as "Ghi chú kèm file", untrusted data that may only hint at what the sheet is and what its columns mean; the result reply then starts with "Đã đọc theo ghi chú kèm file." Trade-off: a question an admin sends less than 5 seconds before a sheet is treated as the sheet's caption and is not answered on its own, and every admin text is answered about 5 seconds after it was sent at the earliest.

Object keys: every object the app writes to the bucket (photos, admin sheets, Excel exports) is stored under `workspaces/<workspace id>/<YYYYMMDD>/<user id>/<object id>.<extension>`, built by `buildObjectKey` (`src/app/storage/build-object-key.ts`). The date is the Vietnam date (`Asia/Ho_Chi_Minh`): the day the person sent the photo or sheet (its `sent_at`), or the day the export was made. The user id is the sender, or the admin who asked for the export. The object id is the message id for a photo, the inbound event id for a sheet (so a retry after a crash before the row is stored writes the same key, not a second object) and a new id for an export. Readers always use the key stored on the row (`messages.image_key`, `message_files.file_key`, `outbound_messages.photo_key`), so older objects keep their old keys and stay readable: photos saved as `<workspace id>/<message id>.<extension>` until the 180-day cleanup removes them, and sheets and exports (`<workspace id>/<message id>.<extension>`, `workspace_<workspace id>/exports/<id>.xlsx`) until removed by hand.

The `photos` group is on only when `PHOTO_STORAGE` and every `S3_*` value except `S3_FORCE_PATH_STYLE` are set. While it is off the service logs `[config] photos is off; missing: <NAMES>.` and photo messages wait; texts are still stored.

| Env var | Default | Meaning |
|---|---|---|
| `PHOTO_STORAGE` | none | `s3` (Cloudflare R2, MinIO or any S3-compatible store) |
| `S3_ENDPOINT` | none | Store URL, for example `https://<account>.r2.cloudflarestorage.com` |
| `S3_REGION` | none | `auto` for R2 |
| `S3_BUCKET` | none | Bucket name |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | none | Access key of the bucket |
| `S3_FORCE_PATH_STYLE` | `false` | `true` for MinIO |
| `PHOTO_RETENTION_DAYS` | `180` | Delete photos older than this many days on each tick. Set to `0` to delete everything immediately. Negative values are rejected at startup. |
| `PHOTO_CLEANUP_BATCH_SIZE` | `50` | Maximum number of photos deleted per tick. Must be between 1 and 500. |

To run with MinIO by hand (never in CI): `docker compose --profile minio up -d --wait minio`. It creates the bucket `photos`. Then set `PHOTO_STORAGE=s3`, `S3_ENDPOINT=http://localhost:9000`, `S3_REGION=us-east-1`, `S3_BUCKET=photos`, `S3_ACCESS_KEY_ID=minioadmin`, `S3_SECRET_ACCESS_KEY=minioadmin` and `S3_FORCE_PATH_STYLE=true`. Set `MINIO_PORT` if port 9000 is taken. The MinIO console is at `http://localhost:9001`. The image is `bitnamilegacy/minio`, because MinIO no longer publishes images on Docker Hub.

## Save what the reader reads

Every text and photo from a person in a workspace goes to one reader. The reader returns a reading. When the reading has work data, the server saves one `records` row per item in one transaction with the saved reply and marks the message `accepted`. When the reader fails (timeout, unavailable or invalid output), nothing is saved, the sender is asked to send again and the message is `unresolved`. A maintenance item without a plate saves nothing from the whole message and asks for the plate. A message from a member with no work data gets the upload-only reply. A photo with no work data gets a reply by its photo problem (`blurry`, `cut_off`, `not_work`, `several_papers`): the message is `accepted`, nothing is saved, and a question in its caption is not answered. `several_papers` means the photo shows two or more separate papers; the reply is "Ảnh này có nhiều giấy tờ nên Trợ lý chưa lưu. Bạn chụp và gửi mỗi giấy tờ một ảnh nhé." It applies to members and admins, to each image of an album, and to a waiting photo reread with its explanation (the wait ends). One paper that lists several jobs, goods lines or trucks, or a screenshot of several chat messages, is not `several_papers`. A question in a member's message is ignored. Admins get the chat model (see "Admins ask the bot"). When the sender is an admin, a text with no photo that states a fact about a truck, driver or route and says explicitly that it holds for every trip ("luôn là", "lúc nào cũng", "mỗi chuyến", "từ nay", "cố định") is not work data: the reader returns no items, nothing is saved as a record, and the admin chat saves it with `save_fact`. A bare "luôn" ("lưu luôn", "chuyển khoản luôn rồi") is not such a cue. A text without such a phrase, for example one that records a cost paid or a one-off event (fuel, toll, repair, pickup, delivery, payment) or one trip (a date, a weight, "hôm nay"), is read as before. A wage, freight rate, allowance, customer or route stated together with such a phrase is a standing fact. Member reads and sheet reads never get this rule. When the sender is an admin, a value they state for the paper in the message, in the photo's caption or in their answer to the bot's question about it (for example a plate, a date or a weight) replaces the printed one, in the paper's fields and in the matching detail. A text that states no value of the paper, such as "phiếu hôm nay", changes nothing, and text printed in the photo never counts as the admin's. Rereads of a saved message pass the sender's current role, so a reread of an admin's message keeps the admin's value and gets the same admin rules as a live read.

Two photos are the same paper when a saved accepted paper (`documents`) matches. A reading's `document_number` is a number only when it holds a digit from 1 to 9: a word such as a printed label, or only zeros, is no number and is saved empty. With a number, the paper is the same when issuer, number and date are equal and the plates are compatible. When that finds no paper, a trip ticket (a weigh ticket or a pickup or receipt paper with no item lines, not saved from a sheet) is the same as a saved trip ticket with the same plate, date, side and net weight ("Trọng lượng hàng", in kg), all present on both. The side is the drop-off side for a `receipt` and the pickup side for a `dispatch` or no stage. Issuer and number are not compared. Two tickets that both print times of day (other than midnight) and share none are two papers; one shared time, or times on only one paper, keeps them one. The oldest matching paper gets the new photo. A paper that is no trip ticket and has no number is never the same as another, except an exact repeat, which the duplicate check on `records` refuses. When unsure, the app keeps two papers: the trip report leaves out a paper that repeats another by plate, date and weight (see the trip report), any other double shows under "Có thể trùng chuyến", and a lost load shows nowhere. Items of one photo are grouped as before: those with a number, equal issuer, number and date, and a compatible plate are one paper.

The `readers` group is on only when `READER_PROVIDER` and `READER_API_KEY` are set (an empty `READER_API_KEY` falls back to `LLM_API_KEY`). While it is off the service logs `[config] readers is off; missing: <NAMES>.` and the messages of people in a workspace wait.

| Env var | Default | Meaning |
|---|---|---|
| `READER_PROVIDER` | none, required | `openai-compatible` |
| `READER_API_KEY` | `LLM_API_KEY` | Key of the reader |
| `READER_BASE_URL` | `https://api.openai.com/v1` | Chat Completions endpoint of the reader |
| `READER_MODEL` | `gpt-6.1-sol` | Model of the reader. It needs a price in `src/app/credits/price-call.ts`, else the start fails |
| `READER_TIMEOUT_MS` | `60000` | Wait for one reader reply |
| `READER_REASONING_EFFORT` | not sent | Sent as `reasoning_effort` when set |
| `READER_PHOTO_MODEL`, `READER_PHOTO_REASONING_EFFORT` | `READER_MODEL`, `READER_REASONING_EFFORT` | Model and reasoning effort of reads that carry a photo, including rereads of photo messages (`gpt-6.1-sol` with `medium` in production). The model needs a price, else the start fails |
| `READER_TEXT_MODEL`, `READER_TEXT_REASONING_EFFORT` | `READER_MODEL`, `READER_REASONING_EFFORT` | Model and reasoning effort of every other read: text messages, admin sheets, rereads of text messages and the detail-number backfill (`gpt-6.1-sol` with `medium` in production). The model needs a price, else the start fails |

Document templates tell the reader what one form of a company must save. A template (`document_templates`, with its fields in `document_template_fields`) belongs to one workspace. It has a name (unique by match key), a kind, an optional issuer company, an optional stage (`dispatch` pickup or `receipt` drop-off), a description of at most 200 characters, a `revision` and up to 20 fields. A field has a name, a type (`text`, `number` or `date`), for a number an optional standard unit (`kg`, `l`, `km` or `vnd`) and a required flag. A workspace holds at most 50 templates; both limits are checked in code under the workspace lock. Only admins define templates, with four chat tools: `propose_document_templates` (a member-text tool: it reads the drivers' accepted papers that are not saved from sheets, groups them by issuer company and kind, and returns the top 5 groups with the paper count, the stage counts and each detail with its type, unit and paper count, or one proposal from a single saved paper), `save_document_template` (the same name key updates the template, replaces its fields and raises `revision`; the issuer is matched to a saved company by name and the result says when none matched), `list_document_templates` and `delete_document_template` (saved papers keep their kind, stage and details). `save_document_template` is a guarded tool: it always waits for the admin's "có" (see "Admins ask the bot"), and the question shows the draft, so the admin confirms once. `list_documents` and `search_records` accept a template name filter. Before every read in a workspace that has templates (member and admin reads, and operator rereads), one call on the text reader (`gpt-6.1-sol`, full-detail image, strict JSON-schema answer, no tools, metered like the read: `photo_read` when the message has a photo, else `text_read`) picks the template the paper matches, or `none`. It sees the templates as a wrapped `document-templates` part (short ids `t1`, `t2`; only name, kind, issuer and description; control characters removed) and the message. A failed or invalid answer is `none`, and the read goes on as before. It logs `[template-pick] picked=<id|none> ms=<n>`. With a pick, the read prompt gets one more rule and the one template, fields included, as a wrapped part, and each item gains `template` (the short id, or null when the paper is another form). Without a pick, the prompt and the schema are the same as before. The server maps the id back to the template: an unknown id becomes null, and a matched item takes the template's kind and, when the template has one, its stage. A saved paper stores the matched template in `documents.template_id` (set to null when the template is deleted). When a driver's or admin's paper matches a template and one of its required fields has no detail with the same name key and a value of the field's type (a number for a number field, a date and time for a date field, a non-empty text otherwise; for a number or date field the detail's meaning may carry the name), the paper is saved as usual and the saved reply gets one more line, `Chưa đọc được: <fields>. Lần sau bạn chụp rõ phần này nhé.`, with the prefix `Mục <n>: ` when the message has several papers. The check runs in the server from the read and the template already in hand; it adds no model call and no query, and it is not stored. Saving a template does not change a saved paper by itself; the backfill below does.

Each admin is offered once to define the company's document templates. The offer is one fixed Vietnamese text (`DOCUMENT_SETUP_OFFER_TEXT` in `src/app/processing/conversation-texts.ts`) and the column `memberships.document_setup_offered_at` records when it was made; drivers get no offer. The join reply of a new admin of a workspace with no template ends with it, and the join sets the column in the same transaction; a new admin of a workspace with templates gets neither. An admin whose column is null, in a workspace with no template, gets it at the end of the next chat answer: the answer transaction checks that the workspace has no template, sets the column only where it is still null, and appends the offer to the stored and sent answer text (before any source card). A failed chat call, a tool-round-limit notice, an empty answer, an answer with a refused change and a scheduled run's answer do not consume the offer. While the workspace has no template and the offer is at most 7 days old, the wrapped `profile` part carries one fixed sentence saying the offer was made and that a short "có" or "ok" accepts it; no user-written text goes in it. The admin prompt then has the model call `propose_document_templates`, or ask for one example photo per form when the company has no saved papers. There are no reminders and no second offer.

Template backfills re-read the saved papers of a form after an admin saves or changes its template. Saving a new template, or one with a changed kind, stage, issuer or field list (name, type or unit), queues one run (`template_backfills`) for the new `revision` in the same transaction as the save; a change to only the name, description or a required flag queues nothing, and a pending run of that template carries over to the new revision. Pending runs of older revisions become `superseded`. A run fixes its candidates when queued, newest first, at most 5000 (the save result says when it is capped): accepted papers that are not from a sheet, with an issuer key and a document number, with a stored source photo (`image_key` set and `image_deleted_at` null) and either the template's `template_id`, the template's issuer company as the issuer party, or (template without issuer) the template's kind. The save result gives the candidate count and whether a re-read started; the propose result gives, per proposal, how many saved papers it would re-read and an estimated credit range taken from the workspace's last 50 `photo_read` calls (the call model that costs most is the read, any cheaper model is the picker). A worker (`src/app/documents/templates/backfills/`) follows the sheet workers: it claims a run with `FOR UPDATE SKIP LOCKED`, a claim token and a five-minute lease, and handles one paper per step. It stops the run as `stopped` when the workspace balance is 0 or below. Otherwise it re-reads the paper's photo message with the workspace's current templates (picker and read both metered as the charged kind `template_backfill`) and takes the one draft whose items all matched this template and whose issuer, document number, date and a compatible plate equal the paper's; none or several count as `unmatched`, a missing photo or a paper that is gone as `skipped`, and a read that fails five times or returns invalid output as `failed`. A matched paper is updated in one transaction under the workspace lock: its facts links and lines are deleted, the draft's lines and meanings are stored, its kind, stage, `template_id`, summary and details are set and its facts are linked again; its plate, date, number, parties, sources and status never change. Every write is fenced by the claim token, `status = 'pending'` and the template's current revision, so a superseded or deleted template discards the read and writes nothing. Failed steps wait 30 s, doubling up to 8 minutes, and a shutdown hands the held run back (token and lease cleared, attempt returned). When the run ends it sends one Vietnamese message through the outbound queue to the admin who saved the template (any admin when that user left): the counts, or the stop reason with how many papers were not re-read. The status change and the message commit together, so the message is sent once, and a run superseded by a newer save sends nothing. A crash between a read and its save can repeat that one billable read.

## Admins ask the bot

A message from an admin goes to the chat model when it has no work data. When it has work data and a question, the server saves the data and sends the saved reply first, then the chat model answers. Unresolved, no-plate and duplicate messages get their fixed replies and never reach the model. Members never reach the model. The model calls three tools, up to 5 rounds: `search_records`, `count_records` and `list_members`. Each tool reloads the caller's membership and refuses anyone who is not a current admin of the workspace. The answer is stored only when the admin's membership row is still the same row and still `admin`. If the chat model fails, the admin gets the failure text; the saved records stay.

The change guard (`AdminTextGuard`) guards six tools only: `remove_member`, `create_invite`, `forget_all`, `forget_all_member_facts`, `rewrite_member_plate` and `save_document_template`. Every other tool runs, also after a lookup. The guard is triggered when the message has a note from a photo or when an earlier call in the same turn was a member-text tool (a tool that returns text from members' papers or messages); history never triggers it, and the turn runs once. A guarded call runs at once only when the guard is not triggered and the admin's current message holds the target as typed, compared without accents and case: the member's display name for `remove_member` and `forget_all_member_facts`, the invited name for `create_invite` with role member, the member's display name and the new plate for `rewrite_member_plate`. `forget_all`, `save_document_template` and an invite with role admin always wait, and a bare "ok" names no target, so it never starts a guarded tool. Any other guarded call is checked by its own argument rules (a failure is refused at once and not stored), then stored in `pending_changes` (one row per admin: `calls` holds each tool name with its arguments, 24 hours of life, a new question replaces the old one) and the tool result tells the model it waits. The server, not the model, writes one question for all waiting calls of the turn from the stored arguments and adds it to the answer: the change, the target by name and its effect (old plate, new plate and number of papers for `rewrite_member_plate`; the role for an invite; the draft with the papers reread and the credit estimate for a template), then "Trả lời Có để làm, Không để bỏ.". The admin's next text message, before any reader call and before a waiting photo question, settles it: a plain yes ("có", "ok", "đồng ý", "đúng", "xác nhận", without accents, case and punctuation) runs the stored calls as stored, a plain no ("không", "ko", "thôi", "hủy") drops them, and any other message drops them and goes on as usual. A photo drops them. The row is deleted in its own transaction before the calls run, so a retried event never runs them twice; the sender must still be a current admin and each tool checks again. The results reach the model as `tool:<name>` data of the yes message, and a new invite code is sent as its own message. `messages.holds_other_text` is no longer written or read; the column stays.

The admin prompt separates a command from a claim. A command is a request to do something, or a statement of what the company's data should be, for example a new wage. The bot does it. It challenges only when the command contradicts itself, names something not saved, gives a value that is hardly possible, contradicts a saved fact or changes more than the admin named, and it challenges once with the saved data and one question. A value typed by the admin beats a value read from a photo. A refusal says what was not done, why and what the admin can do instead. A tool error about arguments (a plate, a date, a company or a member id) says the form expected, and for a plate and a company also what was received. The bot fixes it itself. A claim about what is stored, for example "this month has 1.000 trips", is still checked with the tools. When one request needs more tool rounds than the limit, `TOOL_LOOP_TEXT` tells the admin the request is not finished, that part of it may already be saved, and to split the request by truck, week or company.

Chat calls use OpenAI's Responses API (`/v1/responses`) with `store: false`, so no conversation is kept on OpenAI's side. During one tool loop, a reasoning model's output items, including its encrypted reasoning, are sent back unchanged with the next round. Every chat call in production uses `gpt-6.1-sol` with `medium`. The supported settings are `gpt-6-luna` with `none` and `gpt-6.1-sol` with `medium`.

Trip facts (`save_fact`, `list_facts`, `update_fact`, `delete_fact`) are standing statements with a scope (plate, driver, pickup company, drop-off company, customer) and values. A paper links to a fact when every filled scope field matches: the plate; the driver, as sender or tag; the pickup and drop-off companies by the paper's stage (below); the customer as a party with role `customer`; and, when the fact has a "Hàng hóa" value, the goods. A route fact (one with a pickup or drop-off company) links only trip tickets: accepted papers with stage `dispatch` or `receipt`, or with no stage and a kind whose match key contains `phieucan`, never kind "tin nhắn", papers saved from sheets (`sheet_signature` set) or papers with item-level lines. Each trip links one ticket: a fact with a pickup company takes `dispatch` tickets, where the pickup is an `issuer`, `place` or `supplier` party, and no-stage weigh tickets, where it is the `issuer`, and never `receipt` tickets; a fact with only a drop-off company takes `receipt` tickets, where the drop-off is the `issuer` or `place` (the receiving factory), and no-stage weigh tickets, where it is the `issuer`, and never `dispatch` tickets. On a receipt ticket `customer` is the transport client, matched only by the fact's customer. When a pickup company is set, the drop-off company is shown but not matched. The cost: a trip with only a receipt ticket gets no pickup fact, and a trip with only a dispatch ticket gets no drop-off-only fact. Goods: the fact's "Hàng hóa" text and each document-level (`item IS NULL`) "Hàng hóa" line match when their whole match keys are equal ("xy 01" = "XY01", the same key the identity uses). Otherwise both are lower-cased, made accent-free and split into tokens on anything that is not a letter or digit. A distinctive token has a digit or at least 4 characters. When the fact's goods have distinctive tokens, every one of them must match a ticket token, equal or a prefix of at least 4 characters either way ("đá ABCDE" matches a ticket reading "lấy ABCD"; "XY01" does not match "XY0"; "cát vàng" needs "vang", so it does not match "cát đen"); short generic words are ignored. When they have none (for example "bột đá"), every token must equal a ticket token, so "bột đá" does not match "đá mi". A customer alone is not a scope. A customer named in `save_fact` is also stored as the text value "Khách hàng". A `save_fact` with a pickup or drop-off company is an upsert under the workspace lock: a saved route fact is the same rule when its goods match (the match key of its "Hàng hóa" value, empty when none; a save with goods needs equal goods, a save without goods matches a saved fact with any goods, so restating a route without its goods updates that fact, and several such facts give `ambiguous` with each candidate's goods), the pickup, drop-off and customer are each empty on both or the same company (equal match keys; picked organizations that share one; or one side's picks including an organization that the other side's match key is an alias of; a slot resolved to no company compares by match key only) and the plate and driver are each empty on both or equal. No match adds a fact (`action: "added"`). One match updates it (`action: "updated"`): each named value replaces that value's stored content, new names are added, omitted values stay, the statement becomes the newest statements that fit in 2,000 characters (newest first), `updated_at` is set and links are not rebuilt unless the goods change, except that a slot left unresolved (for example by `split_merged_name`) takes the new call's picks when they hold at least one company, becomes resolved and the fact is relinked (`restored_companies` in the result); `changes` lists each `replaced` (old → new) and `added` value, and a call that changes nothing writes nothing. Several matches change nothing (`action: "ambiguous"`, with each candidate), and a later call with `fact_id` updates that fact only when it has the same identity apart from goods (a goods change through `fact_id` relinks the fact). Facts without a pickup or drop-off are always added. `update_fact` cannot set or clear a pickup, drop-off or customer (a different route is a separate fact); it adds or changes the other values of a route fact, goods included, which is how a message that names no place completes the fact from the recent turns (the prompt finds it with `list_facts` and asks when several fit); it refuses a plate, driver or goods change that would make a route fact equal another saved one; a change of plate, driver or goods relinks the fact. When `save_fact` names a company, one call on the text reader (`gpt-6.1-sol`, JSON-schema answer, no tools, metered as `text_read`) reads the admin's names and the workspace's saved companies (with opaque ids, names and spellings cut to 120 characters) and picks, per slot, every company that is the same business. The picks are stored in `fact_companies` and the slot's `pickup_resolved` / `dropoff_resolved` / `customer_resolved` becomes true; a resolved slot matches a paper only through its picked companies, and a resolved slot with no picks matches nothing. A failed or invalid answer, or more than 300 saved companies, leaves the slot unresolved and the name matching above decides, including refusing an ambiguous name. Each slot logs `[fact-company] slot=<slot> name="…" picked=<n> of <total>` or `… failed, name matching`. `split_merged_name` marks the slots that picked the split company unresolved, relinks those facts by name and tells the admin to save them again. Run `node dist/bootstrap/relink-facts.js <workspace-uuid> [--apply]` in the service shell once after this rule shipped. It fills a missing customer scope from each fact's "Khách hàng" value (the value stays), with `--apply` resolves every unresolved company slot (metered as `operator_backfill`, not charged), recomputes every fact's links under the workspace lock without changing `updated_at`, and prints `<fact id> <links before> → <links after>`. Without `--apply` it changes nothing, and a second run changes nothing.

A trip or trip-cost report ("báo cáo chi phí tháng 11, mỗi dòng một chuyến, các cột …") goes to `export_trip_report_xlsx`, which the server builds from the database; the model only picks the date range (at most 92 days, by document date), an optional plate, a title and up to 40 columns in the admin's order. Each column has a source: a fixed field (`date`, `pickup_date`, `dropoff_date`, `plate`, `route`, `pickup_place`, `dropoff_place`, `customer`, `goods`, `weight_kg`, `pickup_weight_kg`, `dropoff_weight_kg`, `document_number`, `pickup_document_number`, `dropoff_document_number`, `document_kind`, `sender`), `fact_value` (a saved fact value name, refused with the list of known names otherwise), `fact_amount` (a `đ/tấn` value × the weight in kg / 1000 of the paper whose fact gave the rate, rounded to the đồng, blank without a weight) or `none`. The rows are trips, one per trip, not one per paper. A trip has a pickup paper, a drop-off paper, or both. Pickup papers are the report's papers dated `date_from` to `date_to` that are not `receipt` papers: every accepted `dispatch` paper plus every accepted paper without a stage that is a trip ticket (`IS_TRIP_TICKET`, below). A saved route fact never decides which papers are in the report. Pickup papers dated the day before `date_from` are loaded only to take part in pairing, so a receipt on `date_from` whose pickup was the day before is not a trip of its own. Drop-off papers are accepted `receipt` papers that are trip tickets (`IS_TRIP_TICKET` in `src/app/facts/link-facts.ts`, the same condition as route-fact linking: not "tin nhắn", not saved from a sheet, no item-level lines), dated `date_from` to `date_to` + 1 day, of any truck. Receipts dated the day before `date_from` are also loaded, of any truck, only to take part in pairing: like the previous-day pickups they never become a trip of their own, so a previous-day pickup meets its own receipt instead of taking an in-range one. Every kept pickup paper takes part in pairing. No saved fact takes part in pairing: a route fact, right, wrong or missing, changes neither the pairs nor which papers are in the report. A paper's time is the earliest printed line time other than 00:00, else its date (upload time is never used); a receipt is in a pickup's window when it is after the pickup and at most 24 hours later (both times printed), else dated the same or the next day. The AI step pairs every dated pickup that has a plate, truck by truck: for each truck the model reads all of its pickups and receipts, each with an opaque id, date, printed time, kg, ticket number, goods, issuer, customer and the document-level "Ghi chú" line (long texts are cut), inside `<retrieved-data source="trip-papers">`. The prompt says a receipt is the same or next day, after the pickup, that weights are close (usually within 100 kg), that a note printing a weight such as "0/028950" holds the pickup's weight and is the strongest evidence, that the customer hints at the factory, that two entries can be photos of one ticket (pair one), that each receipt is used once, and that a wrong pair is worse than none; the answer is strict JSON, a receipt id or "none" and a reason per pickup. Whole trucks are packed into calls of at most 60 pickups and 60 KB together; a truck with more than 60 pickups is sent alone in one call; a truck over 60 KB by itself is not sent; a truck is never split or trimmed. At most 16 calls run at the same time, each on a dedicated reader built from the photo reader setting (`gpt-6.1-sol` with `medium` in production, 60-second timeout, no retry, metered as `chat_answer`). Code checks every answer: the ids were offered, both papers are of one truck, the receipt is in the pickup's window, two present weights differ by at most 3%, a pickup answered twice is rejected, and a receipt chosen for two pickups is rejected for both; a failed check rejects that pair only. The model's pair wins, and its "none" leaves the pickup unpaired even when the closest-weight rule would pair it. The closest-weight rule is the fallback: a pickup with a plate and a date takes the rule's pair when its truck's call failed, was invalid or was not sent (counted as skipped), or no reader is configured. The rule pairs a pickup with a receipt in its window when both weights exist and differ by at most 3%, and only when each paper is the other's single closest in weight (smallest difference in kg, chosen once over all the possible pairs of the report; two equally close papers are a tie and that paper gets no rule pair; a tie on one paper does not block a clear pair of two others); possible-duplicate pickups (same plate, date and pickup, found before pairing) get no rule pairing, but their possible pairs still count, so another pickup cannot take the receipt a duplicate is closest to. Possible duplicates go to the model with the rest. A pair's method is `rule` for a fallback pair or a pair the rule also makes, else `ai`. The receiver is the ticket's issuer company (skipped when it names two), else its place, never its customer. Each receipt belongs to at most one trip. Unpaired receipts dated `date_from` to `date_to` become drop-off-only trips; a receipt dated `date_to` + 1 day appears only paired with an in-range pickup; unpaired pickups become pickup-only trips. A trip's date is its pickup paper's date, else its drop-off paper's; trips are listed by that date, then plate, then paper id. Per trip: `pickup_date` and `dropoff_date` are each paper's date; `pickup_place` is the pickup of the newest route fact that counts for the trip (below), else the issuer of the pickup paper (a `dispatch` paper or a paper without a stage); `dropoff_place` is the paired receipt's receiver, else the drop-off of the newest route fact that counts for the trip, and the cell holds only that name; `route` is "<pickup place> → <drop-off place>" with "?" for a missing end; `pickup_weight_kg` and `dropoff_weight_kg` are each paper's weight (the first document-level `kg` line meaning "Trọng lượng hàng") and `weight_kg` is the pickup's, else the drop-off's; the two paper numbers are separate fields and `document_number` joins them, pickup first, with " / "; `customer`, `goods`, `document_kind` and `sender` come from the pickup paper, else the drop-off paper, where goods is the winning "Hàng hóa" fact value, else the first document-level "Hàng hóa" line. A fact value on a trip comes from the facts that count for the pickup paper, else from the facts linked to the drop-off paper, so a paired trip never counts one value twice; a drop-off-only trip keeps its receipt's linked values; a pickup and a receipt of one load that fail to pair stay two trips. A fact that counts for a pickup paper is one linked to it that names no drop-off, or whose drop-off name means the receiver of the paired receipt; the same facts give the route pickup name and customer, newest first. After pairing, one call on the pairing reader (metered as `chat_answer`) reads the distinct drop-off names of the facts linked to the paired pickups and the distinct receivers of their receipts with their other spellings (opaque ids, texts cut to 120 characters, no amounts, inside `<retrieved-data source="drop-off-names">`, at most 40 KB: a larger input counts as a failed call) and answers, per drop-off name, the receivers it means or none (a section, plant or branch of the named factory counts; a name "A or B" means both); code accepts only offered ids, and no facts with a drop-off means no call. When the call failed, the receiver is unknown or the pickup has no receipt, a fact with a drop-off counts only when all the pickup's facts name one and the same drop-off, else only facts without a drop-off count. With no fact left the pickup is the issuer, the drop-off the receiver, the customer the printed customer, the goods the printed goods and the money blank. Facts linked to the receipt stay as they are. The service logs `[trip-drop-off] names=<n> matched=<k>` or `[trip-drop-off] failed reason=<reason>`. More than 5,000 pickup papers or 5,000 receipts (the previous day included) is refused; the limit counts every loaded paper, repeats included. After loading and before pairing, the report leaves out the papers that repeat another one, among the pickups and among the receipts separately. A repeat has the same plate, date and weight in kg as another paper, all three present; issuer, number, goods and kind are not compared. Two papers that both print times of day (other than midnight) and share none are not repeats; one shared time, or times on only one paper, makes a repeat (the same time rule as the saving of a photo above). The papers are taken in the order they were saved, and each joins the first group in which it repeats every paper, else it starts a group, so two papers with different times never become one through a third without times. The report keeps the first paper of a group that has a ticket number, else the first one. Only the kept papers take part in pairing, rows, facts, totals, the count of papers without a weight and "Có thể trùng chuyến". Nothing saved changes. A "Ghi chú" sheet lists the `none` columns, the columns blank in every row, the papers waiting for review that would qualify (the same selection, without requiring the accepted status), the papers without a weight, possible duplicates (which stay in the table), the repeated papers left out ("Phiếu gửi trùng, đã bỏ khỏi bảng": the count, or "Không có", then a table with plate, date, side "lấy hàng" or "đổ hàng", kg, the number left out and the number kept, "(không số)" for none; only papers dated `date_from` to `date_to`), the trip counts (both papers, pickup only, drop-off only), how many AI calls ran or failed and how many pickups were not sent (those trucks use the rule), the pairings (plate, date, both paper numbers, method "Khớp trọng lượng" or "AI suy luận ra"), each drop-off name written in the facts with the companies it was matched to (or "không khớp"), a line when that call failed, and the trips without a pickup or without a drop-off paper, headed "Chuyến không ghép được đơn" (the first 300). The result gives the link, `rows` (the trips), `trips_with_both_papers`, `trips_pickup_only`, `trips_drop_off_only`, `paired_by_rule`, `paired_by_ai`, `ai_calls_ran`, `ai_calls_failed`, `ai_rows_skipped`, `repeated_papers_left_out`, rows per plate and the other counts; the reply gives the trip count, the three trip counts, the review count, the number of repeated papers left out when it is not 0, and the link. The service logs `[trip-pairing] rule=<a> ai=<b> ai_calls=<n>` and, per call, `[trip-pairing] ai rows=<r> candidates=<k> seconds=<s>` or `[trip-pairing] ai failed reason=<reason>`. All three Excel tools (`export_report_xlsx`, `export_trip_report_xlsx`, `export_documents_xlsx`) share one house style (`src/app/documents/format-workbook-sheet.ts`): a merged title (bold, size 15, dark blue) and a grey italic info line "Số dòng: N · Tạo lúc: dd/mm/yyyy hh:mm" (Vietnam time, N counts data rows) above a blank row; the header on row 4 in dark blue `#1F3864` with white bold centered wrapped text, frozen; a hair line under each data row and every other row shaded `#F2F5FA`; text top-aligned and wrapped, numbers right-aligned, dates centered; a cell whose whole value is "AI suy luận ra" in dark amber; widths from the displayed text (unit suffix included) between 8 and 50; the filter over the header and data rows; landscape A4, one page wide, the header repeated on each printed page. Each number column has a unit: `vnd` (`#,##0 "đ"`), `kg` (`#,##0 "kg"`), `ton` (`#,##0.00 "tấn"`), `liter` (`#,##0.0 "lít"`), `rate` (kept per cell, with its own unit) or `number` (`#,##0`, `#,##0.00` when not whole). `export_report_xlsx` takes an optional `unit` per column (no unit means `number`, never guessed from the name); the trip report gives `fact_amount` `vnd`, `weight_kg`, `pickup_weight_kg` and `dropoff_weight_kg` `kg`, and a `fact_value` column the unit of its values (all "đ" → `vnd`, all kg → `kg`, all "…/…" → `rate`, mixed or with text → per-cell formats); the document list gives the amount `vnd` and each fact column the same rule. When a column is `vnd`, `kg`, `ton` or `liter`, a "Tổng cộng" row follows the data (bold, light blue, a top line and a double bottom line) with `SUBTOTAL(109, …)` over the data rows of each such column, written with the server's sum as the cached result so viewers that do not recalculate still show it, and Excel's filter changes it to the visible rows. `export_report_xlsx` and `export_trip_report_xlsx` build exactly the columns the admin named, in their order, with no extra columns, rows or sections; the one exception is the trip report, which the server ends with a last column "Cách ghép phiếu" (not counted in the 40-column limit, not chosen by the model, not a target of `sort`): "Khớp trọng lượng" for a pair the closest-weight check made (also when the AI step chose the same pair), "AI suy luận ra" for a pair only the AI step chose, "Không ghép được đơn" for a trip with one paper in the report, so an admin filters one column to check the AI pairs. Saved trip facts change none of the three. Both sheets take the words from one definition (`src/app/trips/trip-report-texts.ts`); the internal methods stay `rule` and `ai`. They take an optional `layout` with only `sort`: up to 3 keys, each a 0-based column index and `asc`/`desc`, used only when the admin asks for an order. Without a sort, `export_report_xlsx` rows go by the first date column ascending, else in the tool's order, and the trip report keeps its trip order (trip date, plate, paper id). An invalid sort (too many keys or a missing column) logs `[report-layout] invalid reason=<reason> fallback` and uses that default; a valid one logs `[report-layout] sort=<keys>`. Older layout fields (`group_by`, `totals`, `summary`, `subtitle`) are accepted and ignored. Sorting is server-side and stable: text is trimmed, then compared with a Vietnamese collator (numeric, accent-insensitive, then exact), numbers and dates by value, numbers before text, blanks always last. The tool result echoes the sort used (`sort_source`: `chosen`, `default` or `invalid`). The trip report's "Ghi chú" sheet draws label rows (label bold, value beside it), blank separators and its sub-tables with the house header and banded rows. When an admin's answer holds a table of more than 5 rows, the bot calls `export_report_xlsx` with the table it filled in from this turn's tool results: a title, columns typed number or text (units in the column names) and the rows. The tool refuses rows that do not match the columns, text in a number column, and tables over 50 columns or 5,000 rows. It stores an `.xlsx` (`bao-cao-<id>.xlsx`, in the house style) under the admin's folder of the day (see "Object keys") and returns a 24-hour link. The reply is plain text with the main result, the link and "link có hiệu lực 24 giờ". Smaller tables stay in the message, one item per line. Admin answers never use markdown, because Zalo shows it as raw symbols.

Company rules (`save_rule`, `list_rules`, `delete_rule`) are standing requests an admin writes in chat, for example "xe lấy hàng ở <A> chỉ đổ ở <B>". They live in `workspace_rules` (`id`, `workspace_id`, `author_user_id`, `rule` of 1 to 1000 characters after trimming, `created_at`; row-level security like `facts`). `save_rule` takes no arguments: the server stores the admin's current message, trimmed, as it was typed, so text read from a photo or a paper never becomes a rule. An empty message, or one over 1000 characters, is refused with that reason. A workspace holds at most 50 rules; the 51st is refused and the result lists the saved ones (the count and the insert run under one advisory lock per workspace). `list_rules` returns each rule with its id and author. `delete_rule` removes one by id and returns its text. `list_rules` is admin text for the admin text guard, and `save_rule` and `delete_rule` are not guarded tools, so the guard does not stop them after a lookup. A rule with a money value is a trip fact (`save_fact`), not a rule. Every admin chat turn gets the rules, oldest first with the author's name, in `<retrieved-data source="company-rules">`, and the prompt tells the model to follow them as standing requests of the company's admins, below the current message and the safety rules. The AI step of the trip report gets the rule texts as `{"rules": [...]}` in its own `<retrieved-data source="company-rules">` part, and its prompt says they are evidence that can forbid or prefer a pair; a rule never adds a pair of two papers that the code checks above reject. When the model call did not run, a pair that only the closest-weight rule found stays as it is and the report note says so. Rules are not used when photos are read and change no saved paper.

Goods names (`join_goods_names`, `list_goods_names`, `remove_goods_name`) let an admin say that several written names of goods are one name, for example "Than Da, Than, Than Đá đều là Than đá". They live in `goods_names` (`id`, `workspace_id`, `author_user_id`, `written_name` of 1 to 200 characters after trimming, `match_key` matching `^[a-z0-9]+$`, `shown_name` of 1 to 80 characters after trimming, `created_at`; unique on `workspace_id` and `match_key`; row-level security like `facts`). The key is built by `buildMatchKey` from the whole goods text, so a written name matches a whole goods text and never a part. `join_goods_names` takes up to 20 written names and one shown name; joining a written name again replaces its shown name, and the result lists each name with the shown name it replaced. `list_goods_names` returns each name with its shown name and author, oldest first. `remove_goods_name` removes one by its written name. `list_goods_names` is admin text for the admin text guard, and `join_goods_names` and `remove_goods_name` are not guarded tools, so the guard does not stop them after a lookup. The trip report's goods cell (from a fact or from the paper, in the same order as before) and the goods the AI pairing step sees use the shown name. Saved papers keep what is printed on them, and goods with no joined name show as they are.

Paper corrections (`correct_document`) let an admin say the right plate, number, date or stage (`dispatch` for pickup, `receipt` for drop-off) of a saved paper, for example "số xe là 00X00002" after a photo. Only admins get the tool. It takes the new values (at least one) and how to point at the papers: `last_photo` (the papers of the newest photo message the same admin sent before the current message, from `document_sources`), the current plate, number or date, and `all_matching`; at least one way to point is required and several together must all match. It finds accepted papers in `documents` itself. No match changes nothing. One match changes. Several matches without `all_matching` change nothing and the result lists up to 20 papers and the total. With `all_matching` every match changes, but a new number is never set on more than one paper, so a new number with several matches changes nothing. A paper that already has the new values is reported as already right. A new plate, number or date must be in text the admin typed, found in code: the current message or that admin's messages in the history the model got (the tool gets them as `typedHistoryTexts`). Text from a photo, a saved note, a tool result or a bot answer does not count. A date counts when its day and month are in the text. The stage needs no such check. A failed check changes nothing. The change runs in one transaction under the workspace records lock. It sets the paper and the plate, number and date of every record of the paper's sources (same message and item index), removes the paper's fact links and matches them again. When an accepted paper with the same issuer, number, date and plate already exists (`documents_issuer_number_date_plate_key`), the sources of the corrected paper move to it, its driver tag moves when the existing paper has none, the corrected paper is deleted and the result says they merged. The paper that stays gets `documents.admin_corrected_at` (timestamptz, null when no admin corrected the paper; no default, no index). The template reread leaves out papers with `admin_corrected_at` when it picks its papers and skips one marked after that, counted as skipped. `correct_document` is member data for the admin text guard, like `search_records`, and is not a change tool, so the guard never refuses it. The tool also sets one printed value of exactly one paper, for example "trọng lượng hàng là 27.080 kg" or "hàng hóa là than đá", from `printed_label` and `printed_value` (with `printed_meaning`, `printed_number` and `printed_unit` for a number). The line is found by its accent-free label among the lines of the whole paper (`item` is null), or by its meaning when no label fits, and the first such line by `line_no` changes, because the reports read the first weight line; a missing line is added. Number, unit and meaning are set as `insertLines` sets them, and a weight in tons is stored in kg. A unit is normalized (`kg`, `KG`, `tấn`, `t`, `l`, `km`, `vnd`) before every check and an unknown unit is refused. A value is a load weight when its label, its meaning or the stored meaning of the line it changes is "Trọng lượng hàng". A load weight needs a number and a weight unit, its meaning is forced to "Trọng lượng hàng", and its text is written from the checked kilograms (for example `27.080 kg`), and a number line is never rewritten without a number. The same label in `documents.details` and in the `details` of the paper's records changes too. The new value must be in text the admin typed, as for a plate. A number counts after removing its separators; a weight is read in Vietnamese format (a dot before exactly 3 digits is thousands, a comma is decimal, any other dot is decimal) with the typed unit, and must equal the kilograms the admin typed. A load weight above 100 tons is refused with that reason. A printed value is only for exactly one paper: with several matches nothing changes and the result lists them. Fact links are matched again, because goods decide them. Values of single item lines are not corrected. The tool also sets one company of exactly one paper, for example "nơi đổ hàng của phiếu này là <nhà máy>", from `company_slot` (`pickup`, `dropoff` or `customer`) and `company_name`. The stage of the paper decides which party it is, in code, as the trip facts do: the pickup of a `dispatch` paper and the drop-off of a `receipt` paper are its issuer, and the customer is the `customer` party. A `dispatch` paper has no drop-off, a `receipt` paper has no pickup, and a pickup or drop-off on a paper with no stage is refused, with the reason (a customer needs no stage). A stage set in the same call counts. The name is matched to the saved companies with the company pick `save_fact` uses (`pickFactCompanies`). Before the transaction, a read-only look finds the paper and checks the stage, then the pick (the only model call) runs outside any transaction, so no model call waits under the records lock and a refused stage or no match costs no model call. The transaction finds the paper and checks the stage again. Two fits change nothing and the tool's error lists them. No fit adds the company as `linkParty` does. The tool replaces the parties of that role on the paper, which are the roles the fact links read for that slot (`issuer`, `place` and `supplier` for a pickup, `issuer` and `place` for a drop-off, `customer` for a customer), with one party of the chosen company, so the trip report and the facts read the new company. A new issuer also changes `issuer_key`; when an accepted paper with the same issuer, number, date and plate then exists, the two merge as above, and the survivor gets the new party. A paper that already has the company is reported as already right. The company name must be in text the admin typed, as for a plate. Fact links are matched again. Renaming a company everywhere and merging or splitting company names are not part of this tool. `rewrite_member_plate` stays for all data of one named driver. A paper's `summary` can still hold the old value; the paper's own value is right.

The `chat` group is on only when `CHAT_PROVIDER`, `LLM_BASE_URL`, `LLM_API_KEY` and `LLM_MODEL` are set. While it is off the service logs `[config] chat is off; missing: <NAMES>.` and an admin's messages wait before the reader runs.

## Credits

Every LLM call of a workspace is one row in `llm_calls`: its kind, model, tokens, cost in USD and credits. 1 credit is $0.001 of price, and the price is the OpenAI cost times 1.5. A charged call lowers `workspaces.credit_balance` by its credits and stores the balance after it. The operator commands `reread-documents` and `backfill-detail-numbers` are recorded with their cost and 0 credits, and never change the balance. Each credit addition is one row in `credit_additions`. Existing workspaces started with 20,000 credits, and a new workspace starts with 0. When a workspace balance is 0 or below, no new action calls an LLM for it. The Zalo intake stores the photos and texts, sends the sender one fixed out-of-credit reply, and leaves the messages `pending`. A scheduled run sends its creator a skip text. The operator commands are never stopped. An action that starts with a positive balance finishes all its LLM calls, so the balance can go below 0. The charge that takes a positive balance to 0 or below queues one notice to each admin of the workspace. Only `src/app/credits/credit-balance.ts` writes `credit_balance`.

The search uses the Postgres `unaccent` extension. The migrations enable it.

### Scheduled tasks

An admin asks for a task that runs once, daily, weekly or monthly (Vietnam time) through `create_scheduled_task`. The tool stores the task as `active` at once, with its first run in `next_run_at`, so there is no draft and no confirmation. The server appends a short summary of each created task to the answer: what it does, when it runs, the first run and how to cancel it. The summary offers no choice. A group has at most 20 `active` tasks. Each creation carries `creation_key = <message id>:<position of the call in the turn>`, with a unique index, so a message processed again after a crash creates no second task. Scheduled runs cannot create tasks. `list_scheduled_tasks` takes a `scope`: `mine` lists the caller's own `active` tasks and `all` lists every `active` task of the workspace with its creator. `cancel_scheduled_task` cancels any `active` task of the caller's workspace and returns its title. The status `draft` stays allowed by the table, but nothing writes it. The migration `0024_remove_schedule_drafts` cancels the drafts that existed and clears the stored `draft_confirm` choices; the code reads any other stored choice than `workspace_pick` as no choice.

#### Scheduled runs and delivery

Every 60 seconds the ticker claims the `active` tasks whose `next_run_at` has passed (and whose `locked_until` is empty or past) with `FOR UPDATE SKIP LOCKED`, locks each for 10 minutes and runs its `instruction` with the creator's admin scope and exactly the tools `search_records`, `count_records`, `maintenance_status` and `list_members`. This runs only while the `chat` group is on. A creator who is no longer an admin (removed, or removed and invited again as a member) turns the task off (`cancelled`). The finish is one transaction that proceeds only when `next_run_at` still equals the claimed value and the creator's membership row is still the same admin row. It stores the result, headed `Lịch "{title}":` on its own line, as a bot message in the creator's chat, queues it with `scheduled_task_id` and moves `next_run_at` to the next occurrence (empty for a one-time task). The run's prompt asks for plain text with no markdown, one item per line, because Zalo shows markdown as raw symbols. An answer that is exactly `KHONG_CO_THONG_BAO` sends nothing. A model error sends `Lịch "{title}" chạy lỗi. Lần chạy sau sẽ thử lại.` The finish also requires the exact `locked_until` its claim set. Ticks never overlap: a tick does not start while another is running. On a deploy, the old instance's shutdown starts no new ticker job, claims no further task, and waits for the tick in progress within its 270-second window. A task still running at the deadline gets its `locked_until` cleared (`[shutdown] handed back task=<id>`, counted in `handed_back`), so the new instance can run it on its next tick and the old instance can no longer finish it. Each run logs `[scheduled-run] started task=<id>` after its claim and `[scheduled-run] finished task=<id>` after its finish commits. A crash leaves the lock to expire and the task runs again once; the conditional finish prevents a double send.

The outbound worker applies the delivery rule to rows that carry `scheduled_task_id` or `requires_open_window` (the photo notices below). When the creator wrote within the last 7 days (less a 10-minute margin) the row is sent as usual. Otherwise, or when Zalo answers that the window is closed (error `-230`, unverified), the row becomes `held`. A held row is never claimed. With `ZALO_REPORT_READY_TEMPLATE_ID` set (the `report-template` group), the first held row after the creator's last message also queues one `template` row with `{"task_title": "…"}` (title cut to 30 characters). Template rows are sent whatever the window. When the person writes again, the inbound handler queues the line `Bạn có {n} tin nhắn chưa nhận được. Trợ lý gửi ngay sau đây.`, then a queued copy of each held row in order, and deletes the held rows.

#### Photo notices

When a member's photo is stored and answered, every current admin of that workspace gets two Zalo messages after the member's own reply: a text and then the photo. The text reads `{display_name} gửi ảnh vào nhóm "{workspace_name}" lúc {HH:mm dd/MM/yyyy}.`, then `Trợ lý đã trả lời {display_name}:`, then the exact reply the member got. Admins' own photos, member texts, captions and photos refused before storage are not announced. The notice rows exist only in `outbound_messages`: each carries `admin_membership_id` (the worker drops it when that membership is gone or no longer an admin) and `requires_open_window`. A row with this marker is held, like a scheduled result, when the admin's 7-day window is closed, and is released at the admin's next message. The notices never enter `messages`, so the admin chat model never sees them. The photo is sent unchanged; Zalo may refuse a photo over about 1 MB, in which case the text still arrives and the image row fails.

For a held photo notice the template parameter `task_title` is `Ảnh mới trong nhóm`.

Owner action: submit this "report ready" template text to Zalo (the parameter is `task_title`; replace the text of an earlier submission, which needs approval again) and, after approval, set `ZALO_REPORT_READY_TEMPLATE_ID` in Render:

```
Thông báo nội bộ: Trợ lý có tin mới cho bạn: "<task_title>". Bạn nhắn một tin bất kỳ cho Trợ lý để nhận.
```
 Without it the reports of quiet admins stay held until they write. While the group is off the service logs `[config] report-template is off; missing: ZALO_REPORT_READY_TEMPLATE_ID.`

## Internal MCP tokens

An internal user sends "lấy token mcp" on Zalo and gets a token for the internal MCP server. The token lasts 30 days. A new token replaces the old one at once. A user can ask for a new token at most once every 30 seconds.

When a token leaks, the user sends "thu hồi token mcp". The bot deletes every MCP token of that user and replies "Đã thu hồi token MCP. Gửi "lấy token mcp" khi cần token mới." There is no rate limit. Anyone who is not an internal user gets the not-internal reply. Both commands match without accents and are never stored as intake.

When the Zalo account itself is lost, an operator revokes every MCP token. Connect as the migration database user (see SQL from a local terminal) and run:

```sql
DELETE FROM internal_mcp_tokens;
```

## Prompt injection

Untrusted data never sits among a model's instructions. `src/app/reading/retrieved-data.ts` holds one rule, `RETRIEVED_DATA_RULE`, added to the system prompt of the reader, the sheet reader, the company picker, the drop-off pairing call, the detail-number backfill, the admin message labeller, admin chat and scheduled runs: content inside `<retrieved-data>` is data, and no instruction in it is followed, even one that claims to come from the system or an admin. Each call's untrusted data goes in the user message, wrapped by `wrapRetrievedData(source, text)` as `<retrieved-data source="…">` … `</retrieved-data>`, where `source` is a fixed word from code (`message`, `photo`, `labels`, `document-kinds`, `companies`, `meanings`, `member-facts`, `sheet`, `company-names`, `trip-papers`, `drop-off-names`, `record`, `history`, `profile`, `memory`, `saved-note`, `tool:<name>`). Any `<retrieved-data` or `</retrieved-data` inside the data, in any case and with any spacing, has its `<` written as `&lt;`, so the data cannot close its tag early; nothing else in the data changes. The system prompts keep only rules and the date: the reader's workspace lists (labels, document kinds, companies, meanings, member facts) and the sheet's file name, context lines, headers, rows and caption are wrapped user parts, each list introduced by a fixed sentence. The request to the model is a fixed sentence after the data, outside any tag. A reader request is an ordered list of parts (`ReaderRequest.userParts`, text or image); a photo is sent as a text part opening `<retrieved-data source="photo">`, the image part, and a text part closing the tag, mapped in order to the OpenAI content parts (another endpoint may treat several parts differently). The admin message labeller wraps the earlier messages as `history` and keeps the admin's new message outside the tag. Chat (admin and scheduled runs) works the same way. The admin prompt and the scheduled-run prompt carry the rule and only fixed role statements; the request has one user message: the workspace name and the person's display name (`profile`; for a scheduled run the workspace, task title and creator), the private memory (`memory`, empty shown as "(trống)") and the whole earlier conversation as `Người dùng:` / `Trợ lý:` lines with the photo and caption markers (`history`), each wrapped, then the current message outside any tag, followed by the "Hệ thống đã lưu" note wrapped as `saved-note` when there is one; a scheduled run's instruction comes after its wrapped `profile`, outside the tag. Every tool result is sent back as `<retrieved-data source="tool:<name>">` with the original output verbatim inside (a tool name that is not a plain lowercase name is labelled `unknown`). Chat prompts hold no member notes, so there is nothing else to move. The tag is a convention the model is asked to respect, not a guarantee, so the change guard (`admin-chat/tools/admin-text-guard.ts`) stays the hard stop for the six risky changes, which wait for the admin's "có".

## Database connections and tool errors

The app's Postgres pool (`src/providers/database/postgres.ts`) uses a 4-second statement timeout and opens every connection with `-c jit=off`: the app runs short queries, and JIT compilation of a large query such as fact linking took about 4 seconds on its own, so the statement was cancelled. In chat and scheduled runs, an exception inside a tool no longer fails the whole message: `run-tool-loop.ts` logs it as `=threw(<ErrorName>: <short message>)` and returns a tool error that tells the model not to call that tool again in this turn. A failed inbound event's `last_error` and its operator alert hold the error name, the database error code when there is one, and a short message, at most 160 characters, with quoted values, long numbers and API keys redacted (`src/app/errors/describe-error.ts`). Money values in `save_fact` and `update_fact` accept the unit as đ, ₫, VND, VNĐ or đồng, alone or with /chuyến, /lượt or /xe (stored as "đ"), or any of those with /tấn (stored as "đ/tấn"), ignoring case, spaces and accents on "tấn" and "chuyến"; any other unit is refused with a reason that names it and shows the expected form.

## Row-level security

The tables `records`, `messages` and `reply_photos` have row-level security (`ENABLE`, not `FORCE`). A row is visible and writable only when its `workspace_id` equals the setting `app.workspace_id`, set with `SET LOCAL` inside each transaction. For a member, `app.owner_user_id` must also equal the row's `user_id`. With no setting, no row is visible. The service connects as the role `app_runtime`: `LOGIN`, no superuser, no `BYPASSRLS`, owns no table, cannot change the schema. The table owner bypasses the policies, so the barrier is on only when `DATABASE_URL` uses `app_runtime`.

At start the service refuses to run as a superuser or a role with `BYPASSRLS`. When its role owns the tables, it logs `[config] database role owns the tables; row-level security is not enforced until DATABASE_URL uses app_runtime.`

On Render nobody runs SQL. A migration creates `app_runtime` without a password when the role does not exist, and always reapplies its grants. Render generates `APP_RUNTIME_PASSWORD`, and the pre-deploy step `migrate.js` sets the role's password to it after the migrations. It logs `[migrate] app_runtime password set`, or `[migrate] failed: could not set the app_runtime password (SQLSTATE <code>)` and exits 1, which cancels the deploy. No line holds the password. The service builds its `DATABASE_URL` from `MIGRATION_DATABASE_URL` with the user `app_runtime` and that password.

Another host sets the password once as the database owner and sets `DATABASE_URL` to the same host and database with the user `app_runtime`:

```sql
ALTER ROLE app_runtime WITH LOGIN PASSWORD '<a long random password>';
```

The password lives only in the environment (`APP_RUNTIME_PASSWORD` or `DATABASE_URL`), never in a migration. `MIGRATION_DATABASE_URL` keeps the database owner's connection string. Check the result with `select current_user, rolsuper, rolbypassrls from pg_roles where rolname = current_user;`, which returns `app_runtime`, `f`, `f`.

```sh
npm run build

When `APP_RUNTIME_PASSWORD` is set, it then sets the `app_runtime` password and logs `[migrate] app_runtime password set`. It never logs the database URL or a password. It exits 1 when `MIGRATION_DATABASE_URL` is empty, without connecting. When the database holds a migration this build does not have (after a rollback), it logs `database is ahead of this build (rollback); skipping migrations` and exits 0.

Every schema change is a new file in `src/app/db/migrations/`, named `NNNN_what_it_does.ts` and exporting `up(pgm)`. The builder offers only `sql(statement)` and `noTransaction()` (`src/app/db/migration-builder.ts`).

Rules:

- **Expand only.** A deploy only adds: new tables (with their indexes and constraints in the same migration), nullable columns or columns with a constant default, concurrent indexes on existing tables, and constraints on existing tables added `NOT VALID` and validated in a later migration. Drops, renames and `NOT NULL` on an existing column come in a later PR, after no running code uses the old shape.
- **Never edit a merged migration.** `ci / migrations` fails when a PR changes, renames or deletes a migration file that already exists on `main`.
- **Locks on existing tables.** Call `lockTables(pgm, ['table', ...])` (`src/app/db/lock-tables.ts`) first. It takes `LOCK TABLE ... NOWAIT` in a fixed table order. When a lock is busy (`55P03`), the runner drops its connection, sleeps 2 s +/- 25 %, and retries. Waiting for another runner's migration lock counts against the same budget. After 60 s in total it exits 1.
- **Timeouts.** Every transactional migration runs with `SET LOCAL lock_timeout = '1s'` and `SET LOCAL statement_timeout = '30s'`.
- **Concurrent indexes.** Call `pgm.noTransaction()` and write `CREATE INDEX CONCURRENTLY`. Such a migration runs with `statement_timeout = '10min'`. Before it builds an index, the runner drops a leftover index of the same name only when that index is invalid. It never drops a valid one. Keep one index build per migration, because a failure outside a transaction leaves the earlier statements applied.
- **Backfills** are separate migrations, in small resumable batches.

## Deploy to Render

`render.yaml` describes one web service (Docker, Singapore) and one Postgres 17 database (Singapore). After the checks pass on a commit on `main` (`autoDeployTrigger: checksPass`), Render builds the `Dockerfile`, runs `node dist/bootstrap/migrate.js` as the pre-deploy command, and starts `node dist/bootstrap/main.js` only if that exits 0. A failed migration cancels the deploy and the previous release keeps serving. The web process never migrates at startup.

During a deploy the old and new instances run side by side until the old one exits. Render gives the old instance up to 300 seconds after `SIGTERM` (`maxShutdownDelaySeconds: 300`). On `SIGTERM` the old instance stops the ticker, closes the HTTP server, stops claiming queue work and logs `[shutdown] started in_progress=<n>`, the number of inbound events it holds. It extends their `locked_until` to 300 seconds after `SIGTERM`, matched by `claim_token`, so the new instance cannot start them. It then keeps working for up to 270 seconds. An event still unfinished then is handed back: `queued`, available at once, with its `claim_token` cleared and one attempt given back, and logged as `[shutdown] handed back event=<id>`. The new instance claims it within seconds, and the cleared token rejects any late write from the old instance. Finally the old instance closes the pool, logs `[shutdown] finished handed_back=<n>` and exits. A failed extension or hand-back is logged, and that event falls back to the 5-minute lock. Every inbound event logs `[inbound] event=<id> done` once its last stage has committed. A run cut off mid-way can repeat an admin tool action when it reruns, as after a crash.

Owner action, before creating the Blueprint:

1. Create an OpenAI API key.
2. Create the Cloudflare R2 bucket `secretary-photos` and an access key pair for it. Note its S3 endpoint.
3. Create the Zalo app. Note its app id and secret key, and the OA secret key.

Then, in a Render Hobby workspace, allow Render's GitHub app on this repository, choose New, Blueprint, pick the repository and fill the 7 prompts:

| Prompt | Value |
|---|---|
| `LLM_API_KEY` | The OpenAI API key. The chat model and the reader use it |
| `S3_ENDPOINT` | The R2 S3 endpoint |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | The R2 access key pair |
| `ZALO_APP_ID`, `ZALO_APP_SECRET` | The Zalo app's id and secret key |
| `ZALO_OA_SECRET` | The OA secret key |

Click Deploy Blueprint. Render fills `MIGRATION_DATABASE_URL` from the database's internal connection string and generates `APP_RUNTIME_PASSWORD` and `CHANNEL_TOKEN_ENCRYPTION_KEY`. The providers, models, base URLs and the bucket name are fixed values in `render.yaml`. No deploy hook, deploy workflow or GitHub secret is involved. The database accepts external connections only from the owner's machines (`187.15.122.223/32` and `15.235.203.116/32` in `ipAllowList`). Render services in the same account and region reach it over the private network. To allow another machine, add its IP to `ipAllowList` in `render.yaml`; a change made only in the dashboard is replaced on the next Blueprint sync.

Never regenerate or edit `APP_RUNTIME_PASSWORD` or `CHANNEL_TOKEN_ENCRYPTION_KEY` in the dashboard. A new encryption key makes the stored Zalo keys unreadable, and `connect-zalo` must run again. A Blueprint sync resets dashboard edits of the fixed values (models, base URLs, providers, the bucket name). Change them in `render.yaml`.

A sync cannot create these. Do them by hand:

- The OpenAI API key.
- The R2 bucket `secretary-photos`, its S3 endpoint and its access keys.
- The Zalo app and its link to the OA: the callback URL `<URL>/oauth/zalo/callback`, the webhook URL `<URL>/webhooks/zalo` with `user_send_text`, `user_send_image` and `user_send_file` on, the OA secret, and the domain verification file if Zalo asks (`ZALO_VERIFIER_FILE_NAME` and `ZALO_VERIFIER_FILE_CONTENT` in the dashboard).
- The `connect-zalo` run in the service shell, approved in a browser.
- The `create-workspace` run in the service shell, once per customer.
- The template approval, then `ZALO_REPORT_READY_TEMPLATE_ID` in the dashboard.
- An alert webhook, if you want one: `ALERT_PROVIDER=webhook` and `ALERT_WEBHOOK_URL` in the dashboard.
- Render's GitHub app access, and the Blueprint creation itself.

Check a deploy: `curl https://<service>.onrender.com/health` returns `200` and a `commit` equal to `git rev-parse origin/main`. Every deploy log holds a `[migrate]` line, then `[migrate] app_runtime password set`. The start log has no `database role owns the tables` line.

Another host needs only the `Dockerfile`: run `node dist/bootstrap/migrate.js` before `node dist/bootstrap/main.js`, set `GIT_COMMIT`, and set `DATABASE_URL` (or `APP_RUNTIME_PASSWORD`, so that `migrate.js` sets the password).

## Code layout and import rules

| Folder | Role | May import |
|---|---|---|
| `src/app/` | Our code | `src/app/`, `src/services/`, Node built-ins, plain libraries such as `zod` |
| `src/services/` | Interfaces our code calls | `src/services/` |
| `src/providers/<role>/` | One class per provider | `src/services/`, vendor packages, Node built-ins |
| `src/bootstrap/` | Composition root and commands | anything |

Vendor packages (`openai`, `@aws-sdk/*`, `pg`, `node-pg-migrate`, `fastify`) are imported only in `src/providers/` and `src/bootstrap/`. Two exceptions: `src/app/db/` may import `src/providers/database/postgres.ts`, and only `src/bootstrap/migrate.ts` may import `src/providers/database/migration-tool.ts`. ESLint enforces all of this. The rules live in `eslint/architecture.js`.
